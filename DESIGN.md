# AI Image Understanding & Content Matching Engine

## Phase 1 — Design Document

## 1. Problem

The system analyzes an image library using a vision model, generates structured metadata for each image, and matches images to blog posts based on semantic meaning rather than filenames or exact keywords.

The system must avoid incorrect recommendations. If the best candidate is not confident enough or does not match the expected subject/category, the system must reject it and provide a human-readable explanation.

Example:

```text
Blog post:
"The behavior of red foxes"

Candidate:
"Gray wolf in a forest"

Decision:
REJECTED

Reason:
Animal category/subject mismatch.
```

---

## 2. Goals

* Understand images using a vision model.
* Generate structured image metadata.
* Validate AI output using a schema.
* Flag low-confidence classifications for review.
* Generate embeddings for image descriptions and blog posts.
* Store embeddings using PostgreSQL with pgvector.
* Rank images using cosine similarity.
* Reject incorrect recommendations using a subject mismatch guard.
* Return `NO CONFIDENT MATCH` when no reliable candidate exists.
* Process image analysis as a background batch job.
* Retry temporary processing failures with exponential backoff.
* Track AI calls and their costs.
* Provide a human review API.
* Measure top-1 precision using a labeled evaluation dataset.

---

## 3. Non-Goals

This project will not build:

* A large image hosting platform.
* A full public-facing frontend.
* A large-scale production vector database.
* Multiple vision-model comparisons.

The project focuses on reliable image understanding and content matching.

## 5. Image Metadata Schema

Each processed image contains structured metadata generated by the vision model.

Example:

```json
{
  "subject": "red fox",
  "category": "animal",
  "description": "A red fox standing in a forest",
  "objects": [
    "fox",
    "trees"
  ],
  "attributes": [
    "orange fur",
    "wild",
    "forest"
  ],
  "confidence": 0.94,
  "safety_flags": []
}
```

The response is validated using Zod before being stored.

The validation schema requires:

* `subject`
* `category`
* `description`
* `objects`
* `attributes`
* `confidence`
* `safety_flags`

Confidence is restricted to the range `0` to `1`.

Images with confidence below `0.50` are marked for review rather than being treated as fully validated results.

---

## 6. Embedding Strategy

Two types of embeddings are generated.

### Image Embeddings

Image metadata is converted into descriptive text containing:

* Subject
* Category
* Description
* Objects
* Attributes

This text is converted into a vector using:

```text
gemini-embedding-001
```

The project stores 1536-dimensional embeddings in PostgreSQL using the `pgvector` extension.

### Post Embeddings

Blog post title/content is converted into an embedding using the same embedding model.

This allows image and post vectors to be compared in the same vector space.

---

## 7. Matching Strategy

The matching service performs vector similarity search between a post embedding and stored image embeddings.

Cosine distance is used by pgvector and converted into similarity:

```text
similarity = 1 - cosine_distance
```

The highest-ranked candidates are then checked using the mismatch guard.

### Decision Thresholds

| Similarity    | Decision |
| ------------- | -------- |
| `>= 0.80`     | Accepted |
| `0.60 - 0.79` | Review   |
| `< 0.60`      | Rejected |

The thresholds can be adjusted as evaluation data grows.

---

## 8. Subject Mismatch Guard

Vector similarity alone is not sufficient because semantically related images can still contain the wrong subject.

For example:

```text
Post: Red fox wildlife photography

Fox image       -> relevant
Forest image    -> rejected: subject mismatch
Dog image       -> rejected: subject mismatch
Mountain image  -> rejected: subject mismatch
```

The mismatch guard checks the expected subject extracted from supported post content against the detected image subject.

A candidate with a clear subject mismatch is rejected even if its embedding similarity is relatively high.

This prevents semantically incorrect images from being accepted only because they are visually or contextually related.

---

## 9. No Confident Match

If no candidate satisfies the required similarity and subject conditions, the system returns:

```text
NO CONFIDENT MATCH
```

Example:

```text
Post:
Quantum Computing Hardware

Available images:
Fox
Dog
Lion
Mountain
Forest

Result:
NO CONFIDENT MATCH
```

This is preferred over returning a misleading image.

## 10. Human Review Workflow

Candidates with moderate similarity can be manually reviewed.

A reviewer can submit:

* `accepted`
* `rejected`

along with an optional comment.

The review API stores the review and updates the corresponding suggestion decision.

Example:

```text
AI Matching
     |
     v
Suggestion: review
     |
     v
Human Reviewer
     |
  +--+--+
  |     |
Accept Reject
```

---

## 11. Background Processing and Retry

Image processing runs through a scheduled background job.

The processor:

* Picks up `pending` images.
* Can retry failed images.
* Allows a maximum of 3 processing attempts.
* Uses exponential backoff.
* Retries after 1 minute following the first failure.
* Retries after 2 minutes following the second failure.
* Leaves the image as `failed` after the maximum attempts.
* Handles Gemini HTTP 429 rate-limit errors through the retry mechanism.

Image records maintain:

```text
status
retry_count
next_retry_at
```

This prevents temporary AI/API failures from permanently failing image processing.

The main database entities are:

### `images`

Stores image records and processing status.

Important statuses include:


### `image_metadata`

Stores structured AI-generated metadata such as:

* Subject

* Attributes
* Description

### `image_vectors`

Stores 1536-dimensional image embeddings.

### `posts`

Stores blog post information.

* Similarity score

### `ai_cost_logs`

Stores AI operation records including:

* Operation
* Model
* Resource ID
* Input tokens
* Output tokens
* Estimated cost
* Timestamp

## 13. Vector Search

The project uses PostgreSQL with the `pgvector` extension.

Vector indexes are created for efficient similarity search.

The matching pipeline retrieves the highest-ranked image candidates based on vector distance and then applies application-level subject validation.

This two-stage approach separates:

1. Semantic candidate retrieval.
2. Reliability and correctness checks.

---

## 14. AI Cost Tracking

Every major AI operation creates a cost log entry.

Tracked operations include:

```text
image_vision
image_embedding
post_embedding
```

Cost logging is intentionally separated from the main processing flow so that a logging failure does not break the image or post processing pipeline.

---

## 15. Error Handling

The system distinguishes between temporary AI/API failures and normal processing failures.

Gemini rate-limit errors such as HTTP 429 are propagated to the background processor so that the retry mechanism can apply backoff.

Other processing errors are recorded against the image as failed.

This allows the background processor to decide whether another attempt should be made.

---

## 16. Evaluation Strategy

Matching quality is evaluated using a labeled dataset containing post/image pairs.

The evaluation script measures:

```text
Top-1 Precision =
Correct Top-1 Predictions / Total Evaluated Cases
```

The current evaluation dataset contains 12 labeled cases.

The evaluation also records whether the selected image was:

* Accepted
* Review
* Rejected

Top-1 ranking accuracy and final acceptance decisions are treated as separate measurements.

This distinction is important because an image can be the correct top-ranked candidate while still requiring human review because its similarity score is below the acceptance threshold.

---

## 17. Reliability Principles

The design follows several reliability principles:

### Semantic Retrieval

Use embeddings to find semantically related candidates.

### Structured Validation

Validate vision output before storing it.

### Mismatch Protection

Do not rely on embedding similarity alone.

### Conservative Decisions

Prefer review or `NO CONFIDENT MATCH` over an incorrect accepted recommendation.

### Retry Handling

Retry temporary failures rather than permanently failing immediately.

### Auditability

Store suggestions, reviews, and AI operation logs for later inspection.
